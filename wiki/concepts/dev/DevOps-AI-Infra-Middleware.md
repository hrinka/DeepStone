# DevOps AI Infra Middleware

Fujitsu × docomo の DevOps AI インフラ構築プロジェクトで使用するミドルウェアの一般的な用途・役割まとめ。
**目的: 各ミドルウェアの「役割」と「なぜそれを選ぶのか」を人に説明できるようにする。** 後日記事化する素材。

このスタックは典型的な **AI/RAG（Retrieval-Augmented Generation）アプリケーション** の構成。
LLM に「正しい知識」を渡すためのデータ基盤、と捉えると全体像がつかみやすい。

---

## 全体像：それぞれの守備範囲

| ミドルウェア | 一言で | データの形 | このスタックでの役割 |
|---|---|---|---|
| **PostgreSQL** | 王道のRDB | 行と列（表） | メタデータ・定義・正本データの保管 |
| **Redis** | 超高速メモリストア | Key-Value | キャッシュ・セッション・一時データ |
| **Qdrant** | ベクトル検索エンジン | ベクトル（数値配列） | 意味（セマンティック）での類似検索 |
| **Neo4j** | グラフDB | ノードと関係（線） | ナレッジグラフ・関係性の表現 |
| **FastAPI** | Python製APIフレームワーク | — | 上記すべてを束ねる入口（Webサーバー） |

> ポイント：**役割が違うから併用する。** 1つのDBで全部やろうとすると、どれも中途半端になる。
> 「正本は Postgres、速度は Redis、意味検索は Qdrant、関係性は Neo4j」という**適材適所の分業**。

---

## PostgreSQL — メタデータ・定義の保管

### 何をするものか
オープンソースの代表的なリレーショナルDB（RDB）。データを **テーブル（行と列）** で管理し、SQL で操作する。
ACID トランザクション・厳密なスキーマ・JOIN による結合が強み。「データの正本（Source of Truth）」を置く場所。

### このプロジェクトでの役割
- ユーザー情報、ドキュメントのメタデータ（タイトル・作成者・更新日・権限）
- システムの設定・定義（どんなパイプラインがあるか、どのモデルを使うか等）
- 「壊れたら困る・整合性が絶対に必要」なデータの保管場所

### なぜ選ぶか
- 信頼性とトランザクション（途中で失敗しても中途半端な状態にならない）
- 厳密なスキーマでデータの品質を担保
- `pgvector` 拡張を入れればベクトル検索もできるが、大規模・高速が要件なら専用の Qdrant に分ける（後述）

---

## Redis — キャッシュ・セッション

### 何をするものか
**インメモリ（メモリ上で動く）** の Key-Value ストア。ディスクではなくメモリに置くので桁違いに速い（マイクロ秒オーダー）。

### このプロジェクトでの役割
- **キャッシュ**：一度計算した結果・DBへの問い合わせ結果を一時保存し、同じ要求に即答する（Postgres/Qdrant への負荷を下げる）
- **セッション**：ログイン状態など「誰が・今・何をしているか」の一時情報
- レート制限、ジョブキュー、一時トークンの保管などにも使える

### なぜ選ぶか
- とにかく速い → ユーザー体験の改善とバックエンドDBの保護
- TTL（有効期限）を設定でき、一時データの自動消去が得意
- 「消えても再生成できるデータ」を置く前提（永続化もできるが本質はキャッシュ層）

## Qdrant — ベクトル検索（なぜ普通のDBじゃダメか）

### 何をするものか
**ベクトル検索エンジン。** テキストや画像を AI（埋め込みモデル）で「意味を表す数値の配列＝ベクトル」に変換し、
**ベクトル同士の近さ＝意味の近さ** として高速に類似検索する。RAG の心臓部。

### なぜ普通のDB（PostgreSQL等）ではダメなのか ★重要

普通のDBの検索は **「完全一致」または「部分一致（LIKE）」** が基本。
つまり **書いてある文字列が合致するか** しか見ていない。意味は理解しない。

| | 普通のDB（キーワード検索） | Qdrant（ベクトル検索） |
|---|---|---|
| 検索の基準 | 文字列が一致するか | **意味が近いか** |
| 「犬」で検索すると | 「犬」を含む文だけヒット | 「ワンちゃん」「柴犬」「ペットの散歩」もヒット |
| 言い換え・表記ゆれ | 拾えない | 拾える |
| 計算方法 | 文字列マッチ | ベクトル間の距離（コサイン類似度等） |

**核心：** ユーザーは LLM に自然な言葉で質問する。「料金プランの変更方法は？」と聞かれたとき、
社内文書に「契約内容のアップグレード手順」と書いてあっても、**文字列は一致しないが意味は同じ。**
普通のDBはこれを拾えないが、Qdrant は「意味が近い」と判断して拾える。これが RAG が成立する理由。

> さらに：ベクトルは数百〜数千次元。普通のDBで「数千次元の近傍探索」を全件計算すると激重。
> Qdrant は **ANN（近似最近傍探索 / HNSW等のアルゴリズム）** で大規模データでも高速に「だいたい一番近いやつ」を返す。これが専用エンジンの存在価値。

### このプロジェクトでの役割
- 社内ドキュメント・ナレッジを埋め込み化して格納
- ユーザーの質問に意味的に近い文書を取り出し → LLM に渡して回答生成（RAG）
- メタデータでのフィルタリング（部署・日付などで絞り込みつつ意味検索）も可能

## Neo4j — ナレッジグラフ（表形式と何が違うか）

### 何をするものか
**グラフデータベース。** データを **ノード（点）と関係（線）** で表現する。
「AさんはBチームに所属」「サービスXはサービスYに依存」のような **「つながり」そのもの** を第一級のデータとして扱う。

### 表形式（RDB）と何が違うのか ★重要

RDB でも関係は表現できる（外部キー＋JOIN）。違いは **「関係をたどる」処理の自然さと速さ。**

| | 表形式（RDB） | Neo4j（グラフ） |
|---|---|---|
| 関係の表し方 | 外部キー＋JOIN | ノード間の「線」そのもの |
| 「友達の友達の友達」を辿る | JOIN を3回重ねる（重く・複雑） | 線を3本たどるだけ（高速・直感的） |
| 多段の関係探索 | 段数が増えるほど指数的に遅くなる | 関係の数に比例（深い探索が得意） |
| 問い | 「この行の値は？」 | 「これとこれはどう繋がっている？」 |

**核心：** RDB は「**個々のデータ**を正確に保管する」のが得意。
グラフDBは「**データ同士の関係**を辿る」のが得意。問いの性質が違う。

例：「この障害の原因となったサービスに依存している全システムを洗い出す」
→ RDB だと依存テーブルを何度も JOIN して辿る必要があり、深さが読めないと書けない。
→ Neo4j なら「依存」の線を辿れと一文（Cypher）で書ける。

### このプロジェクトでの役割
- ナレッジグラフ：概念・ドキュメント・人・システムの **関係性** を構造化
- RAG の高度化（GraphRAG）：ベクトル検索で見つけた情報に、グラフで「関連する周辺知識」を補強
- 依存関係・影響範囲の分析（DevOps 文脈：構成管理・インシデント原因追跡）

> Qdrant は「**意味が似ているもの**」を、Neo4j は「**明示的に繋がっているもの**」を返す。役割が補完関係。

## FastAPI — Python の API フレームワーク

### 何をするものか
Python 製の高速な Web API フレームワーク。クライアント（フロントやLLM）からのリクエストを受け、
上記のミドルウェア群を呼び出して結果を返す **「窓口・司令塔」。**

### 特徴
- **高速**：非同期（async/await）対応。Node.js や Go に匹敵する性能
- **型安全＆自動ドキュメント**：Python の型ヒント＋ Pydantic でリクエスト/レスポンスを検証。Swagger UI（OpenAPI）が自動生成される
- AI/ML 界隈は Python が主流 → モデル・埋め込み処理と同じ言語で書けるのが大きい

### このプロジェクトでの役割
- システムの入口（エンドポイント）
- リクエストを受けて：Redis でキャッシュ確認 → なければ Qdrant で意味検索＆Neo4j で関係取得 → Postgres でメタ確認 → LLM で生成 → 返す、という **オーケストレーション**
- 認証・バリデーション・ロギングの集約点

---

## まとめ：典型的な RAG リクエストの流れ

これを語れれば全体像を理解していると言える：

1. ユーザーが **FastAPI** のエンドポイントに質問を投げる
2. **Redis** で「同じ質問のキャッシュ」があるか確認 → あれば即返す
3. 質問を埋め込みベクトル化し、**Qdrant** で意味的に近い社内文書を取得
4. 必要なら **Neo4j** で関連する周辺知識・関係性を補強（GraphRAG）
5. **PostgreSQL** で文書のメタdata・権限・正本を確認
6. 集めた文脈を LLM に渡して回答を生成
7. 結果を **Redis** にキャッシュして **FastAPI** が返す

> **一言で：** Postgres=正本、Redis=速度、Qdrant=意味、Neo4j=関係、FastAPI=司令塔。
> 「なぜ複数のDBがあるのか」と聞かれたら「**データの形と問いの性質が違うから、適材適所で分業している**」と答えられる。
