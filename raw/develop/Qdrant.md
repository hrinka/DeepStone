## まず全体像：2つのDBの役割分担

```
Neo4j  = 「構造」を記憶する（インフラの依存関係）
Qdrant = 「知識」を記憶する（過去事例・ドキュメント）
```

---

## Qdrantの役割：AIの「記憶・経験」を司る

Qdrantはベクトルデータベースで、**RAG（検索拡張生成）の中核**です。

このシステムでは「AIに障害対応の知識・経験を与える」役割を担います。

```
Qdrantに貯められているもの（想定）：
・過去の障害事例と対応履歴
・運用ドキュメント・ランブック
・IaCのコード例・ベストプラクティス
・エラーログのパターンと原因
・社内の運用ナレッジ
```

---

## 障害対応フローでのQdrantの動き

システム障害が起きた時の流れに沿って見ると、Qdrantの役割がはっきりします。

```
① 障害発生（CloudWatchアラート）
        ↓
② エラー内容をベクトル化
   「RDSの接続がタイムアウトしている」
        ↓
③ 【Qdrantの出番】
   このエラーと類似した
   過去事例・ドキュメントを検索
   → 「過去に似た障害があった」
   → 「その時はコネクションプール設定が原因だった」
   → 「対応したIaCコードはこれ」
        ↓
④ 検索結果をLLMのコンテキストに渡す
        ↓
⑤ LLMが原因分析・改善案・IaC生成
   （Qdrantの知識を根拠にする）
```

---

## なぜQdrantが必要なのか：ハルシネーション対策

ここが一番重要です。LLM単体では**それっぽい嘘**を生成します。

```
❌ Qdrantなし（LLM単体）
「RDSのタイムアウトですね。
 おそらくこう直せばいいと思います」
→ 一般論・根拠なし・ハルシネーションのリスク

✅ Qdrantあり（RAG構成）
「過去の障害事例DB（Qdrant）を検索した結果、
 類似ケースが3件見つかりました。
 いずれもコネクションプール設定が原因で、
 この時のIaC修正はこうでした」
→ 実際のデータが根拠・信頼できる
```

## Neo4jとQdrantの連携イメージ

2つのDBが組み合わさって威力を発揮します。

```
障害発生：「EC2のCPUが急上昇」

Neo4j（構造を辿る）：
「このEC2に依存しているのは
 RDSとALB。影響範囲はこのサービス群」
        +
Qdrant（経験を引き出す）：
「過去のCPU急上昇事例では
 こういう原因とこういう対処をした」
        ↓
LLMが両方を統合して判断：
「影響範囲はこれ（Neo4j）、
 過去事例から原因はこれ（Qdrant）、
 IaC修正案はこれ」
```

```
Neo4j  → いま何が繋がっているか（リアルタイムの構造）
Qdrant → 過去に何が起きたか（蓄積された経験）
```

## ベクトル検索の仕組み（簡単に）

Qdrantが「類似事例を探せる」のはベクトル検索のおかげです。

```
テキストを数値の配列（ベクトル）に変換
「RDS接続タイムアウト」→ [0.2, 0.8, 0.1, ...]

意味が近いテキストは
ベクトルも近くなる

「DB接続が切れる」も近いベクトルになる
→ 文言が違っても「意味が似た」事例を探せる
```

これがキーワード検索との決定的な違いです。「タイムアウト」という単語が一致しなくても、**意味的に似た過去事例**を引っ張ってこられます。
